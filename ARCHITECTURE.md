# Архитектура Lab

```text
iOS / Android / Web (Expo)
          │ HTTPS + JWT
          ▼
    Go REST API ──────── DeepSeek API (опционально, минимум данных)
       │      │
       │      └── OCR: pdftotext / Tesseract
       ▼
 MongoDB (профили, гибкие показатели, ACL, консультации)
       │
       └── private file volume (оригинальные PDF/фото)
```

## Почему MongoDB

Состав показателей существенно отличается между ОАК, биохимией, гормонами, генетикой и бланками разных лабораторий. Массив `markers` внутри документа анализа позволяет хранить этот набор без миграции таблиц при появлении нового показателя. При этом пользователи, доступы и консультации имеют стабильную структуру и индексы. При росте проекта разумен гибрид: PostgreSQL для identity/ACL/audit и MongoDB либо JSONB для результатов.

## Основные потоки

1. Пациент регистрируется или входит.
2. Клиент получает фото/PDF и отправляет multipart-запрос.
3. API сохраняет оригинал и queued-анализ атомарно, возвращает `202`, а Mongo-backed worker захватывает задание с lease. Из PDF сначала читается текстовый слой; сканированные страницы передаются Tesseract. Этапы и retries сохраняются в анализе, поэтому обработка переживает рестарт и масштабируется несколькими worker-процессами. При одиночной загрузке клиент остаётся на экране прогресса и опрашивает состояние до экрана проверки: HTTP-запрос не удерживается, но для пользователя это один непрерывный сценарий.
4. Лабораторные таблицы сохраняются как проверяемые `markers`, а УЗИ/КТ/МРТ — как отдельный `report` с дословными описанием и заключением. Отсутствующее заключение не достраивается. Сырой OCR-текст с персональными данными не передаётся внешней языковой модели; модель получает только подтверждённые пользователем структурированные показатели.
5. Пациент всегда видит историю. Он выбирает врача, выдаёт доступ конкретному анализу и создаёт запрос.
6. Врач видит только явно открытые ему результаты и отвечает в консультации.
7. Web позволяет открыть оригинал и печатать; мобильный клиент вызывает системное меню отправки.

## Следующие этапы до production

- S3-совместимое зашифрованное object storage вместо локального volume;
- подтверждение email, MFA, refresh tokens и отзыв сессий;
- верификация врача и администраторский контур;
- отдельная модель согласий, отзыв доступа и неизменяемый audit log;
- антивирусная/CDR-проверка вложений;
- словарь LOINC/локальные справочники единиц и сопоставление диапазонов по полу/возрасту;
- тренды показателей и ручное подтверждение результата пользователем;
- уведомления APNS/FCM и email provider;
- TLS, secret manager, резервные копии и наблюдаемость;
- оценка требований 152-ФЗ/GDPR/HIPAA и классификации медицинского ПО для выбранного рынка.
